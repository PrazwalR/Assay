## [ORACLE-1] Short sequencer outages produce a stale-but-"fresh" reference that under-charges informed flow, contradicting the documented "over-charges, never under-charges" safety claim
**Severity**: High
**Category**: evm-audit-oracles
**Location**: `ChainlinkReferenceAdapter.referenceSqrtPriceX96()` (src/oracle/ChainlinkReferenceAdapter.sol:132-149), `AssayHook._advanceStateInPlace()` (src/AssayHook.sol:320-369), `PoolTwap.update()`/`withinBound()` (src/libraries/PoolTwap.sol:37-79); claim tested is in `SECURITY.md`, "No L2 sequencer uptime check."
**Description**: `SECURITY.md` accepts the missing L2 sequencer-uptime check, reasoning: "the aggregator cannot be updated while the sequencer is down, so the existing staleness check fires... the pool over-charges after a restart rather than under-charging." This implicitly assumes the outage lasts *longer* than `MAX_AGE_SECONDS` (deployed `3600`, one hour). It does not hold for shorter outages — the realistic case for L2 sequencer incidents.

While Base's sequencer is down, no L2 blocks are produced, so `block.timestamp` freezes along with everything hook-side: `PoolTwap.update` (sampled once per block) is equally frozen, and no swaps can occur. On resumption, `block.timestamp - updatedAt` reflects `(outage duration) + (pre-outage age)`; for any outage shorter than roughly that difference from `MAX_AGE_SECONDS`, this stays under the bound, so `fresh = true` is returned with a price unchanged since before the outage. Because the pool's own `twapTickX32` anchor is *also* frozen, `PoolTwap.withinBound` sees no new disagreement, and the deviation cap doesn't trip either — both of its inputs moved together (i.e., not at all).

If the real off-chain price moved during the outage, an arbitrageur trading the pool toward the new true price is captured by `Mispricing.signedTicks` as trading toward a reference that is itself stale in the same direction — near-zero apparent drift, quoted near `baseFeePips` (500) instead of `maxFeePips` (10,000) — the opposite of the intended response to informed flow.
**Proof of Concept**: (1) Pool trades normally, reference/anchor/pool tick mutually consistent. (2) Sequencer halts ~20 minutes (under the 3600s bound) — confirmed live that the feed's `updatedAt` only advances on a new posted round. (3) Real ETH price moves during the halt. (4) Sequencer resumes; staleness check still passes, deviation cap passes (frozen anchor agrees with frozen reference). (5) Arbitrageur swaps toward the new true price, quoted near `baseFeePips` instead of `maxFeePips`, repeatable each block until Chainlink's next update lands. No existing test exercises "outage shorter than `MAX_AGE_SECONDS` with pool+reference frozen together."
**Recommendation**: Read Chainlink's L2 sequencer uptime feed and enforce a grace period (≥ `MAX_AGE_SECONDS`) after any restart before treating the reference as usable, forcing `maxFeePips` for the whole grace window regardless of outage length. Revise `SECURITY.md` to state the actual precondition ("holds only when outage ≥ stale bound").

## [ORACLE-2] `ChainlinkReferenceAdapter.referenceSqrtPriceX96()` can revert on small positive feed answers, violating its own "never reverts" contract — reachable via the live feed's own `minAnswer` sentinel
**Severity**: Medium
**Category**: evm-audit-oracles
**Location**: `ChainlinkReferenceAdapter._toSqrtPriceX96()` (src/oracle/ChainlinkReferenceAdapter.sol:156-166), called from `referenceSqrtPriceX96()` (lines 132-149)
**Description**: The adapter's header claims "Every failure mode is reported as `fresh = false` rather than raised," and `IReferencePriceOracle` states implementations "MUST NOT revert." But `referenceSqrtPriceX96()` only wraps the external call `FEED.latestRoundData()` in `try/catch` — the post-processing `_toSqrtPriceX96(uint256(answer))` runs inside the success body but is **not** covered by `catch` (Solidity try/catch only guards the external call itself). `_toSqrtPriceX96` computes `FullMath.mulDiv(PRICE_NUMERATOR, 1<<192, answer)`. Uniswap's `FullMath.mulDiv` has `require(denominator > prod1)`, which reverts whenever `answer <= floor(PRICE_NUMERATOR / 2^64)`. For the deployed config (`PRICE_NUMERATOR = 10^20`), that threshold is `answer <= 5`. Verified via Foundry PoC: reverts for `answer` in `{1,2,3,4,5}`, succeeds from `6` onward — matching the calculated threshold exactly. `answer=1` is the live deployed feed's actual `minAnswer`, confirmed on-chain (`cast call` on the underlying aggregator's `minAnswer()` returns `1`). Currently masked, not exploited: `AssayHook._readReference()` wraps the *entire* call to `REFERENCE_ORACLE.referenceSqrtPriceX96()` in its own try/catch, so this internal revert is caught there, degrading to `(0,false)`. So no live swap currently reverts — but the property holds by accident of a second defensive layer, not because the documented adapter-level guarantee is actually true in isolation. Existing fuzz tests give false assurance: every fixture uses equal-decimal pairs against an 8-decimal feed (`PRICE_NUMERATOR = 1e8`, ~12 orders of magnitude below the ~1.8e19 activation threshold), so the bug can never trigger in tests. The deployed numerator (`1e20`) is never exercised by any test.
**Proof of Concept**: Verified locally with a temporary test using the exact deployed numerator: constructed the adapter with `(feed, 3600, 1e20, C0, 6, C1, 18)`, set `feed.setAnswer(1)` (the live feed's actual on-chain `minAnswer()`), called `adapter.referenceSqrtPriceX96()` — reverts. Boundary scan confirmed `answer` 1-5 revert, 6-10 succeed, exactly matching `floor(1e20 / 2^64) = 5`.
**Recommendation**: Bound-check before the multiply: precompute `answer <= PRICE_NUMERATOR / (1<<64)` as an immutable threshold at construction and `return (0, false)` if the feed's answer falls at or below it, before calling `_toSqrtPriceX96`. Update `SECURITY.md`'s min/max-answer section to reflect the actual failure mode. Add a unit test constructing the adapter with the deployed decimal configuration and fuzzing low `answer` values.

## [ORACLE-3] Deviation-cap tick-to-price-ratio is miscalculated in `.env`/`SECURITY.md`: 20,000 ticks is ~7.39x, not ~2.7x
**Severity**: Low
**Category**: evm-audit-oracles
**Location**: `AssayConfig.maxReferenceDeviationTicks` (deployed `20000`); reasoning in `.env` and `SECURITY.md` "Reference deviation cap" section.
**Description**: `.env`/`SECURITY.md` justify the cap with "20000 ticks is roughly a 2.7x price ratio (~172%)... An order-of-magnitude feed error is ~92,000+ ticks... The gap is wide enough..." Computing `1.0001^20000` precisely gives ≈7.39x (+639%), not 2.7x. The deployed cap is more permissive than the developers believe: a reference wrong by 2.7x-7.39x — a range the stated mental model implies should be rejected — is in fact accepted. This doesn't break the cap's core purpose (true order-of-magnitude errors, ~46,104+ ticks, are still far above 20,000 and rejected), but it narrows the actual safety margin relative to what's documented.
**Proof of Concept**: Not a standalone exploit — a documentation/reasoning defect widening an already-acknowledged residual limitation.
**Recommendation**: Correct the `.env` comment and `SECURITY.md` to state the accurate conversion (20,000 ticks ≈ 7.39x / +639%). Re-decide with correct numbers: lower the constant to ~9,933 ticks if 2.7x tolerance was the actual design intent, or keep 20,000 but rewrite the justification.

**Scope notes**: `VarianceEwma.sol`/`OrderFlowImbalance.sol` confirmed dead code, not reviewed. `DeployOracle.s.sol` derives `PRICE_NUMERATOR` from live `decimals()` calls, no hardcoded-decimals issue found for feed reuse (aside from ORACLE-2). Live on-chain checks performed: feed decimals (8), current answer/updatedAt fresh, `minAnswer=1`/`maxAnswer≈9.58e52` on the underlying aggregator.
