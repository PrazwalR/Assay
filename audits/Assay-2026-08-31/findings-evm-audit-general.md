## [G-1] Gas-griefing the once-per-block reference read stalls the pool's dynamic fee at maxFeePips indefinitely
**Severity**: Medium
**Category**: evm-audit-general
**Location**: `AssayHook._advanceStateInPlace()` (src/AssayHook.sol:320-369), `AssayHook._readReference()` (src/AssayHook.sol:176-185), `ChainlinkReferenceAdapter.referenceSqrtPriceX96()` (src/oracle/ChainlinkReferenceAdapter.sol:132-149)
**Description**: `_readReference()` wraps the call to `REFERENCE_ORACLE.referenceSqrtPriceX96()` in `try/catch` with no explicit gas stipend, forwarding the default 63/64 of remaining gas. The adapter makes a further nested external call (`FEED.latestRoundData()`) plus a `mulDiv`/`sqrt`. Since the attacker fully controls the transaction's gas limit, they can (via off-chain simulation) pick a limit that lets execution reach this call but starves the nested chain, forcing an OOG revert caught by `AssayHook`'s outer `catch`, reported as `(0, false)`. Critically, `state.lastBlock = uint32(block.number)` is set *before* the read, unconditionally, at the top of the once-per-block branch — so once this forced failure happens on the first swap of a block, no other swap in that block retries the read. `FeeBlend.quote` returns `maxFeePips` whenever `referenceFresh` is false, so every subsequent swap that block is charged the static ceiling instead of the drift-based fee. An attacker can repeat this cheaply every block (e.g. via dust swaps) to permanently defeat the mechanism, with the real oracle staying perfectly healthy throughout, and no admin able to intervene by design.
**Proof of Concept**: (1) Binary-search a tx gas limit `G` such that the external call to the adapter starves mid-execution but the outer `afterSwap` still completes. (2) Submit a small swap with gas `G` as the first tx touching the pool in a new block. (3) Observe `ReferenceFreshnessChanged(poolId, false)` despite a healthy feed. (4) All swaps for the rest of that block are quoted `maxFeePips`. (5) Repeat every block to keep the pool permanently pinned at the ceiling fee.
**Recommendation**: Forward an explicit, generous gas stipend to the oracle call (`REFERENCE_ORACLE.referenceSqrtPriceX96{gas: X}()`) so starving it also starves an attacker's own transaction prohibitively; and/or decouple `lastBlock` advancement from read success so a failed read doesn't block a later, honestly-gassed retry within the same block.

## [G-2] `int128(uint128(amount))` downcast in the toxicity-surcharge donation path is not provably exact at its own stated boundary
**Severity**: Low
**Category**: evm-audit-general
**Location**: `AssayHook._donateCeilingOverflow()` (src/AssayHook.sol:439-441), `ToxicitySurcharge.unspecifiedAmount()` (src/libraries/ToxicitySurcharge.sol:27-44)
**Description**: The final line returns `int128(uint128(amount))` with the comment "Bounded above by `notional`, itself an int128 magnitude, so the cast is exact." But the magnitude of an `int128` ranges over `[0, 2**127]` (reached when the raw delta is exactly `type(int128).min`), while `int128` itself only represents up to `2**127-1`. Solidity's same-width `int128(uint128(x))` conversion bit-reinterprets rather than reverts, so `int128(uint128(2**127))` silently yields `type(int128).min` — a large negative value — contradicting the comment. Reaching this requires a swap delta of exactly `type(int128).min` (~1.7×10^38 token units) combined with `overflowPips` saturating near `MAX_OVERFLOW_PIPS`, which is unrealistic for any real token pair the hook's immutable oracle is bound to, but the invariant as documented is technically false.
**Proof of Concept**: Not practically reachable given realistic token supplies for the intended pair. If it were reached: `_donateCeilingOverflow` would `donate()` a huge positive amount but return a large negative `int128` hook delta, desynchronizing the donation from its supposed exact offset and corrupting swap settlement.
**Recommendation**: Replace the comment-only guarantee with an enforced one, e.g. `SafeCast.toInt128(amount)`, so any future change to the upstream bound fails loudly rather than silently flipping sign.

## [G-3] Chainlink staleness check silently treats a future `updatedAt` as fresh
**Severity**: Low
**Category**: evm-audit-general
**Location**: `ChainlinkReferenceAdapter.referenceSqrtPriceX96()`, src/oracle/ChainlinkReferenceAdapter.sol:140
**Description**: `if (block.timestamp > updatedAt && block.timestamp - updatedAt > MAX_AGE_SECONDS) return (0, false);` only checks the age bound when `block.timestamp > updatedAt`. If a feed ever reports `updatedAt >= block.timestamp`, the entire staleness check is skipped and the reading is treated as fresh no matter how implausible. Every other guard in this file has an explicit comment justifying its design; this asymmetry has none, suggesting it's an oversight rather than intent. Unreachable against a well-behaved same-chain Chainlink feed today (timestamps are chain-monotonic), but becomes relevant if the feed is compromised/misconfigured or a future adapter swaps in a source with different timestamp semantics — at which point staleness could never be detected via this check again.
**Proof of Concept**: Not exploitable against a normal same-chain feed today; dormant failure mode. If `latestRoundData()` ever returned `updatedAt > block.timestamp`, the reading would be treated as fresh forever regardless of actual age.
**Recommendation**: `if (updatedAt > block.timestamp || block.timestamp - updatedAt > MAX_AGE_SECONDS) return (0, false);` — treats a future timestamp as invalid rather than skipping the check, and avoids underflow via short-circuit evaluation.

## Checklist items confirmed inapplicable (verified, not assumed)
- Storage pointer reassignment no-op: `_advanceStateInPlace` correctly uses a memory struct passed by reference, with an explicit `_poolState[poolId] = state;` writeback in `_afterSwap` — the correct pattern, not the footgun.
- Struct deletion with nested mappings: `PoolState` has no mappings; never `delete`d.
- Mixed accounting / balance introspection: absent everywhere; no custody, `donate()`'s debit is exactly repaid in the same call.
- Merkle proofs, `msg.value`/loops/multicall, delegatecall, force-feeding, pause, upgradeability, `abi.encodePacked` collisions, rebasing/fee-on-transfer, ERC4626 inflation: none present, confirmed by direct grep and reading — no such patterns exist in `src/`.
- PUSH0 on L2: Base/Base Sepolia supports PUSH0 since Canyon; not a blocker.
- Reveal-gap steering: a swap's own quoted fee is fixed from state cached before that transaction runs; the reference re-read in `_afterSwap` only affects future transactions, so a swap cannot steer its own fee via a value it reveals within its own execution.
